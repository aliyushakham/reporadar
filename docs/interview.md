# Как рассказывать о проекте

## Короткое описание для резюме

Разработала RepoRadar — локальный инструмент изучения Python-репозиториев:
AST-анализ и граф вызовов, поиск по коду и Markdown, анализ влияния изменений,
версионирование в SQLite и автоматизация через n8n. Реализовала CLI, HTTP API,
веб-интерфейс, тесты и воспроизводимое сравнение методов поиска.

Используй эту формулировку после самостоятельного разбора и воспроизведения проекта.
Не выдавай результаты небольшого искусственного набора за качество на реальных
промышленных репозиториях. Не заявляй обучение моделей — его здесь нет.

## Что нужно суметь объяснить

- Чем AST отличается от поиска регулярными выражениями по исходному коду?
- Почему `client.save()` нельзя связать с любой функцией `save`?
- Как BFS строит кратчайший путь вызывающих функций и останавливается на цикле?
- Как строится BM25 и зачем нужен baseline поиска по идентификаторам?
- Почему поисковый score не является вероятностью правильного ответа?
- Почему русские запросы работают только в пределах словаря?
- Чем отличается связь документации с кодом от доказанного противоречия?
- Зачем SQLite одновременно хранит JSON снимка и нормализованные таблицы?
- Почему смена номера строки не считается изменением функции?
- Как workflow переживает недоступность сервиса и где сохраняется результат?
- Какие ограничения мешают считать анализатор полноценным компилятором?

## Самостоятельная проверка перед откликом

1. Проиндексируй один свой Python-проект и вручную проверь пять связей.
2. Напиши десять собственных запросов; сохрани релевантные функции и ошибки поиска.
3. Добавь один тест для найденного пограничного случая.
4. Внеси изменение в отдельный пример и объясни diff и цепочку affected callers.
5. Выполни SQL-запрос о самых часто вызываемых функциях.
6. Запусти workflow n8n и объясни его ветку ошибки.

Разработка выполнена с помощью AI-инструментов; профессиональная ценность для
портфолио зависит от понимания решений, проверки результатов и способности их менять.
